# Research: 모바일 친화성 전방위 점검 및 개선 계획

- 날짜: 2026-07-23
- 요청 원문: 앱을 휴대폰에서도 많이 볼 것 같아. 그래서 UI/UX가 모바일 친화적이어야해. 핸드폰에서 원활하게 사용하기 좋게 앱이 잘 만들어져있는지 전방위적으로 검토해서 필요하다면 개선 계획도 세워줘

## 요약

프론트엔드 5개 페이지(Dashboard·Transactions·Budgets·Assets·Settings)와 공통 컴포넌트(layout·dialog·table·calendar·chart·date/select 입력)를 직접 읽어 모바일 대응을 점검했다. **기반은 견고하다** — 뷰포트 메타가 있고(`frontend/index.html:6`), 레이아웃은 데스크톱 사이드바(md+)/모바일 하단 내비로 분기하며(`AppLayout.tsx:19,51`), 표는 `ScrollArea`로 가로 스크롤 처리(`table.tsx:8-15`), 다이얼로그는 반응형 폭·하단 버튼 세로 적층(`dialog.tsx:64,110`), 차트는 `ResizeObserver`+`contain:inline-size`로 폭 전파를 차단한다(`EChart.tsx:33,48`). 여러 페이지가 이미 모바일 분기(예산 컬럼 숨김, 자산 그리드 적층, 설정 탭 내부 스크롤)를 갖췄다.

개선 여지는 **페이지가 깨지는 수준이 아니라 조작성·가독성** 쪽에 집중된다: (1) 아이콘 액션 버튼이 28~32px로 권장 터치 타깃(44px)보다 작고 인접 배치되어 오탭 위험, (2) 거래 추가/수정 다이얼로그가 필드가 많아 짧은 뷰포트에서 세로로 잘릴 수 있음(다른 다이얼로그와 달리 내부 스크롤 미적용), (3) 거래 내역 표(8열)는 375px에서 항상 가로 스크롤이 필요해 모바일 정보 밀도가 나쁨, (4) 일부 헤더/행이 좁은 폭에서 긴 텍스트+버튼으로 빠듯, (5) 캘린더 셀 금액 가독성 저하.

사용자 결정에 따라 이 계획은 **명확한 결함 수정 + UX 향상**을 포함하며, 거래 내역 표는 **모바일 전용 카드 뷰를 신설**한다(큰 구조 변경은 이 항목에 한정).

## 영향도

- **`frontend/src/components/ui/dialog.tsx`** (다이얼로그 세로 스크롤을 컴포넌트 기본값으로 손대는 경우): 앱 전역 모든 다이얼로그(대시보드 세부내역, 거래 폼/import/월삭제, 예산 복사확인, 자산 평가/삭제/목표, 설정 3탭)에 영향. 안전을 위해 **공통 컴포넌트 회귀 방지**가 필요 — 기존에 정상 표시되던 짧은 다이얼로그의 레이아웃이 바뀌지 않아야 함. 대안으로 거래 폼 다이얼로그에만 국소 적용(import와 동일 방식)하면 영향 범위 최소화. 구현 재량.
- **`frontend/src/components/ui/button.tsx`** (터치 타깃을 사이즈 변형 자체로 키우는 경우): 데스크톱 포함 전역 버튼 크기에 영향 → 데스크톱 레이아웃 회귀 위험. 히트영역만 넓히는 방식(`AssetsPage.tsx:193` 패턴)이면 시각 크기 불변이라 영향 국소화. 구현 재량.
- **`frontend/src/pages/TransactionsPage.tsx`** (모바일 카드 뷰 신설): 기존 `@tanstack/react-table` 정렬·페이지네이션 로직은 데스크톱 표에 그대로 두고, 모바일 카드 뷰는 동일 `items`/`table.getRowModel()` 데이터를 재사용해야 정렬·페이지네이션 일관. 표/카드 전환은 `sm` 브레이크포인트로 CSS 분기(둘 다 렌더 후 `hidden`/`sm:block`) 또는 조건부 렌더 — 구현 재량. 편집/삭제 핸들러(`openEdit`, `remove`)는 공유.
- 그 외 헤더/행/캘린더 수정은 각 페이지·컴포넌트 국소 변경으로 부작용 없음.
- 백엔드·API·데이터 계약 변경 **없음** — 순수 프론트엔드 표현 계층.

## 성공 기준 (Acceptance Criteria)

> 모바일 뷰포트 확인은 **/qa 단계에서** 브라우저 도구(375px 뷰포트)로 수행한다. /implement는 코드 변경과 `npm run build`/`npm run lint` 통과까지 책임진다.

- [ ] AC-1 (전역 무결성): 375px 뷰포트에서 5개 페이지(대시보드·자산 상태·지출/수입 내역·예산 설정·기준정보 관리) 모두 **페이지 가로 스크롤·요소 겹침·텍스트 잘림이 없다** — /qa 단계에서 각 페이지를 375px로 열어 확인. (표·차트 등 본질적으로 넓은 콘텐츠의 *내부* 가로 스크롤은 허용.)
- [ ] AC-2 (터치 타깃): 표·목록·카드의 아이콘 액션 버튼(수정/삭제 등)이 모바일에서 **최소 44×44px의 유효 터치(히트) 영역**을 갖는다 — 시각 크기 유지 여부는 구현 재량이나, 인접 버튼을 눌렀을 때 의도한 버튼이 활성화되어야 함. /qa 단계에서 거래 표/카드, 설정 각 탭 행, 자산 목표·평가 이력의 액션 버튼을 375px에서 탭해 오탭 없이 동작하는지 확인.
- [ ] AC-3 (긴 폼 다이얼로그 세로 스크롤): 거래 추가/수정 다이얼로그가 **짧은 뷰포트(375×667)에서 헤더·모든 입력 필드·푸터 버튼에 스크롤로 도달 가능**하고 상/하단이 잘리지 않는다 — /qa 단계에서 375×667로 거래 추가 다이얼로그를 열고, 구분을 '이체'로 바꿔 필드가 최대인 상태에서 최상단 '날짜'부터 최하단 '추가/취소' 버튼까지 스크롤로 모두 접근되는지 확인. (다른 다이얼로그의 기존 정상 표시가 깨지지 않아야 함 — AC-1로 함께 확인.)
- [ ] AC-4 (거래 내역 모바일 카드 뷰): 지출/수입 내역 페이지의 테이블 뷰가 **sm 미만에서 카드 목록으로 표시**되어 날짜·구분·카테고리·금액·수정/삭제 액션이 가로 스크롤 없이 한 화면에 보인다. sm 이상에서는 기존 표가 표시된다. 정렬·페이지네이션 결과가 카드 뷰에도 반영된다 — /qa 단계에서 375px(카드)와 768px(표)를 각각 열어 확인하고, 정렬 토글 후 카드 순서가 바뀌는지 확인.
- [ ] AC-5 (헤더/행 빠듯함 해소): 자산 목표 카드 헤더·목표 행, 기준정보 카테고리 탭 헤더가 **375px에서 버튼과 텍스트가 겹치거나 잘리지 않고**, 긴 금액/이름은 줄바꿈 또는 말줄임으로 수용된다 — /qa 단계에서 375px로 자산 상태(목표 존재 상태)·기준정보 카테고리 탭을 열어 확인.
- [ ] AC-6 (캘린더 가독성): 캘린더 뷰의 일별 셀에서 수입/지출 금액이 **375px에서 셀 밖으로 넘치지 않고** 읽을 수 있다(줄바꿈/축약 허용) — /qa 단계에서 375px로 거래 캘린더 뷰(금액이 큰 날 포함)를 확인.
- [ ] AC-7 (회귀 없음): `cd frontend && npm run build`(tsc+vite)와 `npm run lint`가 통과한다 — /implement 단계에서 실행해 확인.
