# Research: 엑셀 업로드 스텝 분리 — 자산계정 매핑 선행 후 거래 검토

- 날짜: 2026-07-24
- 요청 원문: 지금 입/출금 내역을 excel 업로드할 때, 내역을 불러와서 한번에 업로드하면서 자산계정도 추가하거나 업데이트 하는거 같은데, 이를 스텝을 나누면 좋겠어. 먼저 자산계정 매핑을 먼저하고 이 자산이 신규인지 기존에 있는 다른 자산계정과 매핑이 가능한지 먼저 설정한 뒤 입출금 내역에 대해서 검토하고 업로드 되도록 하고싶어

## 요약
현재 업로드는 `파일/월/구성원 입력 → 미리보기(이체 검토·평가액) → 확정` 2스텝이고, 자산 계정은 사용자 개입 없이 **확정 시점에 자동 처리**된다. 거래 결제수단명은 `ensure_account(name)`이 업로드 구성원 스코프에서 이름 완전일치로만 찾고, 없으면 `guess_account_type()` 휴리스틱 유형으로 즉시 생성한다(`backend/app/routers/transactions.py:545-559`, `backend/app/excel_import.py:256-265`). 뱅샐현황 부동산·대출도 상품명 완전일치로만 매칭하고 미매칭이면 계정을 새로 만든다(`backend/app/routers/transactions.py:675-736`). 그래서 표기가 조금만 달라도("롯데카드" vs "롯데 카드") 같은 자산이 중복 계정으로 갈라지고, 유형도 휴리스틱대로 굳어진다. 해결은 미리보기와 거래 검토 사이에 **자산계정 매핑 스텝**을 넣어, 엑셀에 등장하는 모든 계정 소스명(결제수단·부동산 상품명·대출 상품명)을 나열하고 소스마다 `기존 계정에 연결 / 새로 만들기(유형 지정) / 이번엔 제외`를 사용자가 정하게 하는 것이다. 매핑 확정 시 계정을 즉시 생성·연결하므로, 이어지는 이체 검토 스텝의 "상대 계정" 드롭다운(`frontend/src/pages/TransactionsPage.tsx:1598-1604`)에서 방금 만든 계정도 바로 고를 수 있다. 매핑 결과는 마지막 `POST /transactions/import` 호출에 함께 전달해, 이름 재매칭이 아니라 확정된 계정 id로 적재하고 제외 소스의 행은 건너뛴 사유와 함께 결과에 남긴다.

## 영향도
- **백엔드 `transactions.py`**: `preview_import` 응답 확장, 매핑 확정용 엔드포인트 신설, `import_transactions`의 계정 해석 경로(`ensure_account`·평가액·부채) 변경. 임포트 라우터 외 다른 라우터는 계정을 id로만 다루므로 영향 없음.
- **백엔드 `schemas.py`**: 임포트 스키마 추가(응답 필드 추가는 하위호환, 요청 필드는 기본값으로 선택).
- **하위호환**: 매핑 정보를 보내지 않는 호출(구 클라이언트·직접 API 사용)은 기존 동작(이름 일치 → 없으면 휴리스틱 자동 생성)을 그대로 유지해야 한다. 그렇지 않으면 기존 업로드 경로가 깨진다.
- **DB**: 스키마 변경 없음 — 매핑을 저장하지 않기로 결정했으므로 신규 테이블·마이그레이션 불필요.
- **프론트 `TransactionsPage.tsx`**: 업로드 다이얼로그가 3스텝(+결과)로 늘어 다이얼로그 높이·너비 분기(`:1406-1410`)와 스크롤 처리에 영향. 모바일 375px에서 매핑 행(소스명 + 동작 선택 + 계정/유형 선택)이 겹치거나 잘리지 않아야 함.
- **자산 계정 데이터**: 매핑 확정 시 계정이 즉시 생성되므로, 이후 업로드를 취소하면 계정만 남는다(사용자 확인된 트레이드오프). 결과/안내 문구로 이 사실을 알려야 오해가 없다.
- **영향 없음**: 카테고리 처리(`ensure_category`), 월 교체 삭제 로직(`transactions.py:507-518`), analytics·valuations 라우터, 자산 페이지(계정을 id로 조회).

## 성공 기준 (Acceptance Criteria)
- [ ] AC-1: 미리보기 응답이 엑셀에 등장하는 **모든 계정 소스**를 반환한다 — 거래 결제수단명(수입/지출 행 + 이체 검토 행), 뱅샐현황 부동산 상품명, 대출 상품명이 각각 소스로 포함되고, 소스마다 (a) 업로드 구성원 스코프에서 이름 완전일치하는 기존 계정 id(없으면 null), (b) 기본 제안 유형, (c) 거래 소스면 해당 결제수단의 엑셀 행 수, 평가/부채 소스면 금액이 함께 온다 — 샘플 .xlsx로 `POST /transactions/import/preview` 호출 후 응답 확인.
- [ ] AC-2: 업로드 다이얼로그가 `입력 → 자산계정 매핑 → 거래 검토 → 결과` 순으로 진행되며, 매핑 스텝은 소스가 하나라도 있으면 항상 표시된다(전부 기존 계정에 일치하는 경우에도 "연결됨" 상태로 확인) — 브라우저에서 업로드 실행해 스텝 순서 확인.
- [ ] AC-3: 매핑 스텝에서 각 소스에 대해 `기존 계정에 연결` / `새로 만들기(유형 선택)` / `이번엔 제외` 중 하나를 고를 수 있고, 기본값은 (완전일치 계정 있으면 그 계정에 연결, 없으면 새로 만들기 + 추정 유형)이다 — 브라우저에서 각 선택지 조작 확인.
- [ ] AC-4: 이름이 정확히 일치하지 않아도 기존 계정으로 연결할 수 있다 — 예: DB에 "롯데카드"(card)가 있고 엑셀 결제수단이 "롯데 카드"일 때, 매핑 스텝에서 "롯데카드"를 골라 확정하면 해당 월 거래가 **새 계정을 만들지 않고** 기존 "롯데카드" 계정에 연결된다. 임포트 후 결과의 `created_accounts`에 "롯데 카드"가 없고, 거래의 `account_id`가 기존 계정인지로 확인.
- [ ] AC-5: 매핑 확정 시 `새로 만들기` 계정이 즉시 생성되어, 이어지는 이체 검토 스텝의 상대 계정 드롭다운에서 선택 가능하다 — 신규 계정명을 포함한 파일로 업로드해 검토 스텝 드롭다운에 해당 계정이 나타나는지 브라우저에서 확인.
- [ ] AC-6: `제외`로 표시한 결제수단의 거래는 한 건도 등록되지 않고, 결과의 건너뜀 목록에 사유와 함께 남는다 — 특정 결제수단을 제외하고 업로드한 뒤 해당 계정 거래 0건 + `skipped`에 제외 사유 표시로 확인.
- [ ] AC-7: `제외`로 표시한 부동산·대출 상품은 계정도 평가액도 생성·갱신되지 않는다 — 제외 후 임포트해 `valuation_count`/`loan_count`가 제외분만큼 줄고 해당 계정이 만들어지지 않음을 확인.
- [ ] AC-8: 평가액/부채 소스는 유형이 맞는 계정으로만 연결된다 — 부동산 소스의 기존 계정 후보에 `real_estate`가 아닌 계정, 대출 소스 후보에 `loan`이 아닌 계정이 나타나지 않고, 서버에서도 잘못된 유형을 지정하면 422로 거부된다 — API 직접 호출로 확인.
- [ ] AC-9: 매핑에서 정한 유형이 그대로 반영된다 — 휴리스틱이 `other`로 추정할 이름(예: "네이버페이")을 `e_money`로 지정해 확정하면 생성된 계정의 `type`이 `e_money`다 — 설정>자산 계정 또는 `GET /accounts`로 확인.
- [ ] AC-10: 매핑 정보를 보내지 않는 `POST /transactions/import` 호출은 기존과 동일하게 동작한다(이름 일치 → 없으면 휴리스틱 자동 생성) — 매핑 필드를 생략한 임포트 요청이 성공하고 거래·계정이 종전대로 만들어지는지로 확인.
- [ ] AC-11: 실패·재시도 시 데이터가 어긋나지 않는다 — 매핑 확정 중 오류(예: 같은 이름·유형 계정 중복)가 나면 사용자에게 메시지가 보이고 매핑 스텝에 머문다. 확정 후 최종 임포트가 실패해도 거래는 부분 적재되지 않는다(단일 트랜잭션 유지) — 오류 상황 재현으로 확인.
- [ ] AC-12: 매핑 확정으로 계정이 먼저 생성된다는 점이 UI에 안내된다 — 매핑 스텝 문구에 "여기서 확정하면 계정이 바로 만들어져요(업로드를 취소해도 계정은 남아요)" 취지의 안내가 있는지 화면에서 확인.
- [ ] AC-13(모바일): 375px 뷰포트에서 매핑 스텝이 가로 스크롤·요소 겹침·잘림 없이 표시되고, 선택 컨트롤이 터치 가능한 크기를 유지한다 — **/qa 단계에서** 브라우저 도구로 375px 리사이즈 후 업로드 다이얼로그를 매핑 스텝까지 진행해 확인.

## 결정 사항 및 출처
- [사용자 확인] 매핑 후보로 보여줄 기존 계정 범위 → "업로드 구성원 소유 계정만" : 직전 작업에서 확정한 구성원 스코프 원칙(`transactions.py:523-530`)을 매핑 후보에도 그대로 적용.
- [사용자 확인] 매핑 스텝에서 다룰 대상 → "결제수단 + 뱅샐현황 부동산/대출 상품명 전부" : 자동 생성되는 모든 계정 경로(`transactions.py:545-559,675-736`)가 사용자 승인을 거치도록 소스 목록에 포함.
- [사용자 확인] 매핑 저장/재사용 → "저장하지 않음(매번 매핑)" : 별칭 테이블·마이그레이션·관리 UI를 범위에서 제외. 한 번 연결하면 계정이 생기므로 다음 업로드부터는 완전일치로 자동 해결.
- [사용자 확인] 제외 옵션 → "제공 — 해당 소스의 거래를 전부 건너뜀" : AC-6/AC-7로 계약화하고 건너뛴 사유를 결과에 노출.
- [사용자 확인] 신규 계정 생성 시점 → "매핑 확정 시 즉시 생성" : 이체 검토 스텝의 상대 계정 드롭다운(`TransactionsPage.tsx:1598-1604`)이 DB 계정만 후보로 쓰므로, 선생성이 배선을 단순화. 취소 시 계정이 남는 점은 AC-12로 안내.
- [기술 결정] 매핑 스텝은 소스가 있으면 항상 표시 : 요청의 "먼저 자산계정 매핑을 먼저 하고 … 설정한 뒤"에 부합. 전부 완전일치인 경우에도 확인 화면으로 노출한다.
- [기술 결정] 매핑 확정은 전용 엔드포인트 1회 호출로 처리(개별 `POST /accounts` 반복 호출 대신) : 여러 계정 생성의 원자성과 소스 종류별 유형 제약(부동산=real_estate, 대출=loan) 검증을 서버 한 곳에 모으기 위함.
- [기술 결정] 매핑 스텝의 신규 생성 유형에서 `easy_pay`(간편결제)는 제외 : `AccountCreate`가 `linked_account_id`를 필수로 요구하므로(`schemas.py:53-62`) 업로드 마법사에서 연결 계정까지 고르게 하면 복잡도가 커진다. 기존 easy_pay 계정에 **연결**하는 것은 허용.
- [기술 결정] 매핑 미전달 요청은 기존 자동 생성 동작으로 폴백 : 요청 필드를 선택값으로 두어 기존 API 계약을 깨지 않는다(AC-10).
- [기술 결정] 최종 임포트에도 확정 매핑을 함께 전달 : 매핑 확정과 임포트 사이에 계정이 바뀔 수 있고, 이름 재매칭은 "다른 이름의 기존 계정에 연결"(AC-4)을 표현할 수 없다.
- [기술 결정] 매핑 결정의 키 이름·JSON 구조, 소스 종류 표현 방식, 유사 계정 추천 알고리즘 적용 여부는 구현 재량 : AC는 외부 동작만 고정한다.
