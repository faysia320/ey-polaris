# Research: 거래 묶기(연결) — 계좌 간 이체·카드 환불 쌍을 연결로 표시하고 통계에서 상쇄

- 날짜: 2026-07-23
- 요청 원문: 수입/지출 내역에서 거래건을 묶을수 있는 기능이 필요해. 예를들면 `2026-06-08 수입 이체 +50,000,000원 신한 주거래 우대통장(저축예금) 으니 이영은 [이체→수입: 이체]` / `2026-06-08 지출 이체 -50,000,000원 우리직장인재테크 저축예금(수수료우대형 으니 신한이영은 [이체→지출: 이체]` 이런 건이야. 이건 하나로 합쳐 보면 A통장에서 B통장으로 이체된거나 다름 없는거지. 그 외로 카드 결제 후 환불된 건이라던가 이런것도 있을테고 말이야. 어떤식으로 처리하면 좋을까?

## 요약

이미 엑셀 업로드 검토에서 **각각 수입·지출로 따로 저장된 두 거래**를, 사후에 하나의 "묶음"으로 **연결**해 (1) 목록에서 함께 묶여 보이게 하고 (2) 수입/지출 통계에서 상쇄시키는 기능이다. 사용자는 **원본 2건을 그대로 보존하고 연결 관계로 표시**하는 방식을 택했다(병합/삭제 아님 — 되돌리기 쉬움 우선). 묶음 유형은 두 가지다: **이체 묶음**(서로 다른 계정 간 이동 — 두 건 모두 수입/지출 통계에서 제외)과 **환불 묶음**(카드 결제 + 환불 — 지출에서 환불액을 차감한 순지출만 통계에 반영). 앱에는 이미 `kind='transfer'` 단일 행 모델이 있지만, 그것은 "처음부터 이체로 입력/적재"하는 경로이고, 이번 요청은 "이미 저장된 income/expense 두 행을 사후 연결"하는 별개 경로다.

핵심 이점: 원본 income/expense 거래는 이미 각자의 계정 잔액에 ±로 반영되어 있으므로(`analytics.py:120-127`), 이체·환불 묶음 **모두 계정 잔액·자산 추이는 이미 정확**하다. 따라서 수정 대상은 **수입/지출 통계 집계(대시보드·AI 리포트)뿐**이고, 자산 잔액/추이 로직은 손대지 않는다. 대상 선택은 목록에서 사용자가 직접 2건을 체크해 "묶기"를 실행한다.

## 영향도

- `analytics.py` `dashboard`·`_month_stats` — **변경 필수**. 이체 묶음 2건은 income/expense/카테고리/예산 spent 집계에서 제외, 환불 묶음은 지출 건에서 환불액을 차감한 순지출로 반영. 두 함수가 규칙을 공유해야 대시보드와 AI 리포트가 일치한다.
- `analytics.py` `assets`(잔액·추이) — **변경 없음**. 원본 income/expense가 이미 각 계정에 ±로 반영되어 이체·환불 묶음 모두 잔액이 정확(요약·근거 참조). 명세에서 "의도적으로 손대지 않음"으로 기록.
- `transactions.py` `_to_out` / `schemas.TransactionOut` / `types.ts` `Transaction` — 묶음 정보 필드 추가로 응답 계약이 확장됨(기존 소비처는 옵셔널이라 하위호환).
- `TransactionsPage.tsx` 테이블·모바일 카드·캘린더 상세 목록 — 선택 UI/묶음 표시 추가. 기존 정렬·페이지네이션·필터와 공존해야 함.
- DB 마이그레이션(신규 0010) — 스키마 추가. `alembic upgrade/downgrade` 정상 동작 필요.
- 예산 진행률(dashboard `budgets`)은 `spent_by_major`(analytics.py:63) 파생이므로, 카테고리 집계에 상쇄가 반영되면 자동 정합(별도 수정 불필요).

## 성공 기준 (Acceptance Criteria)

- [ ] AC-1: 목록에서 수입 1건 + 지출 1건(서로 다른 계정, 같은 금액)을 선택해 "이체"로 묶으면, **원본 2건이 그대로 보존**된 채 두 거래가 하나의 묶음으로 연결되고 목록에서 묶음임이 시각적으로 표시된다 — 묶기 후 거래 목록(API 응답의 묶음 필드)과 화면 표시로 확인.
- [ ] AC-2: 이체로 묶인 두 건은 대시보드의 `income_total`·`expense_total`·`expense_by_category`·예산 `spent`에서 **모두 제외**된다. 반면 두 계정의 잔액과 자산 추이는 묶기 전과 **동일**하게 유지된다 — 묶기 전/후 대시보드(`GET /analytics/dashboard`)와 자산(`GET /analytics/assets`) 응답 비교로 확인.
- [ ] AC-3: 지출 1건 + 환불(수입) 1건을 "환불"로 묶으면, 대시보드 지출 집계에는 **(지출액 − 환불액)의 순지출**만 반영되고 환불 수입은 `income_total`에서 제외되며, 원본 2건은 보존된다. 환불액이 지출액과 같으면 해당 지출은 집계상 0이 된다 — 묶기 전/후 대시보드 응답 비교로 확인.
- [ ] AC-4: 묶음을 해제하면 두 거래가 다시 독립 거래로 돌아가 수입/지출 통계에 묶기 전과 동일하게 반영된다 — 해제 후 대시보드 응답이 최초 상태와 일치함을 확인.
- [ ] AC-5: 규칙에 맞지 않는 조합은 묶기가 거부되고 사람이 읽을 수 있는 오류가 표시되며 데이터는 변경되지 않는다. 최소 거부 케이스: (a) 선택이 2건이 아님, (b) 같은 방향 2건(수입+수입 또는 지출+지출), (c) 이체인데 금액 불일치, (d) 환불인데 환불액이 지출액 초과, (e) 이미 다른 묶음에 속한 거래 포함 — 각 케이스에서 오류 응답/메시지와 데이터 불변을 확인.
- [ ] AC-6: 묶기·해제는 각각 단일 DB 트랜잭션으로 처리되어 중간 실패 시 원본과 묶음 상태가 일관되게 보존된다 — 코드 검토로 확인.
- [ ] AC-7: AI 리포트 월간 집계(`_month_stats`)가 대시보드와 동일한 상쇄 규칙을 적용해 두 화면의 수입/지출·순저축 수치가 일치한다 — 같은 월에 대해 `_month_stats` 산출값과 대시보드 응답이 일치함을 확인.
- [ ] AC-8: 신규 마이그레이션이 `alembic upgrade head` / `downgrade`에서 오류 없이 적용·복원된다 — 두 명령 실행으로 확인.
- [ ] AC-9 (모바일): 목록의 행 선택(체크박스), "묶기" 버튼, 묶기 확인 다이얼로그, 묶음 시각 표시, 해제 조작이 **375px 뷰포트에서 가로 스크롤·요소 겹침·잘림 없이** 조작 가능하다 — **/qa 단계에서** 브라우저 도구로 확인.

## 결정 사항 및 출처

- [사용자 확인] 이체 묶기 결과 형태 → **원본 2건 유지 + 연결(묶음) 표시**, 통계에서 상쇄(병합/삭제 아님) : 링크 그룹 모델을 도입하고 원본 income/expense 행은 보존한다.
- [사용자 확인] 카드 환불 등 상쇄 쌍 처리 → **원본 유지 + 연결 표시로 상쇄** : 지출에서 환불액을 차감한 순지출만 통계에 반영, 원본 2건 보존.
- [사용자 확인] 묶을 대상 선택 방식 → **목록에서 사용자가 직접 2건 선택** : 자동 후보 탐지는 이번 범위 밖.
- [기술 결정] 계정 잔액·자산 추이(`analytics.py:assets`) → **수정하지 않음** : 원본 income/expense가 이미 각 계정에 ±로 반영되어 이체·환불 묶음 모두 잔액이 정확(요약·영향도 근거).
- [기술 결정] 묶음 유형 판정 → 서로 다른 계정=이체, 같은 계정=환불을 **기본 제안**하되 다이얼로그에서 사용자 확정. 이체는 반대 방향 2건·금액 동일 요구, 환불은 지출+환불 수입·환불액 ≤ 지출액 요구.
- [기술 결정] 묶음 범위 → **정확히 2건 묶음**(수입 1 + 지출 1). 3건 이상(분할 이체·다중 환불)은 이번 범위 밖.
- [기술 결정] 원본 카테고리/kind → 변경하지 않고 연결만 추가(되돌리기 시 원상 복원이 자명해짐).
- [기술 결정] 묶음 데이터 표현(전용 테이블 vs 컬럼), 응답 필드 키 이름, 묶음 시각 표시의 구체적 UI(배지/색/그룹핑) → 구현 재량. 외부 계약(보존·상쇄·해제·거부 규칙)은 위 AC로 고정.
